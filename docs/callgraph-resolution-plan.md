# План: доведение разрешения вызовов в графе

> (2000-3500) выполнен. Что осталось нерешённым — в конце файла и в

## Где мы находимся

Замеры — на корпусе `go-rest-api` (3232 файла `.go`, 10 552 узла графа,
сборка 1,05 с). Это Go-сервис с внедрением зависимостей, где почти каждый
межпакетный вызов идёт через фабрику, поэтому корпус хорошо показывает
именно ту слабость, которую мы закрываем.

| резолюция | до работ | сейчас |
|---|---:|---:|
| `Unresolved` | 56 739 | 64 000 |
| `Scope` | 10 203 | 35 700 |
| `Unique` | 48 647 | 13 700 |
| `Receiver` | 25 | 13 126 |
| `FactoryReceiver` | — | 9 460 |
| `NameOnly` (догадка) | 16 698 | **8 449** |
| `SameFile` | 3 125 | 576 |

Рост `Unresolved` — это не потеря: там вызовы в stdlib и третьи стороны
(`assert`, `fmt`, `time`, `strings`) и конверсии типов `model.Uuid(x)`,
которые раньше подавались как вызовы функций этого репозитория.

## Из чего состоит остаток

Классификация всех 8449 рёбер `NameOnly` по форме места вызова:

| # | класс | рёбер | пример |
|---|---|---:|---|
| A | переменная, тип которой не прочитан | 2924 | `feeAmount.Bigint()`, `context.SetServiceApiKeyHeaders(...)` |
| B | цепочка на результате вызова, не подходящего под фабричные имена | 2055 | `accountRepo(context.C).FindByUuid(uuid)` |
| C | цепочка через поле: `self.<поле>.<метод>()` | 1605 | `self.C.Logger().SendError(err)` |
| D | `self.<метод>()`, где метод — на встроенной структуре | 1328 | `self.AddTask(...)` при `struct AccountInterest { goscheduler.BaseCronScheduler }` |
| E | переменная из многозначного присваивания | 537 | `batchService, err := ...` затем `batchService.Submit("")` |

Общий знаменатель у всех пяти: тип **написан** в исходнике — в объявлении
типа, в списке результатов функции или в поле структуры, — но граф хранит
только функции и потому его не видит.

## Э1. Индекс типов (фундамент)

Без него ни один из остальных этапов не делается.

- Новый модуль `src/callgraph/types.rs`; в `CallGraph` — поля
  `types: FastMap<String, Vec<TypeDecl>>` и
  `types_by_file: FastMap<String, Vec<String>>` для инвалидации.
- `TypeDecl { name, file_path, package_dir, kind: Struct | Interface | Alias,
  fields: Vec<Field { name, type_name, embedded: bool }>,
  methods: Vec<String> }` — `methods` заполняется только для интерфейсов
  (нужен Э5).
- Сбор — внутри уже существующего обхода `extract_functions`, чтобы не
  платить за второй проход по дереву. Go: `type_declaration` → `type_spec`
  → `struct_type` / `interface_type`. Поле без имени в `field_declaration`
  — встроенный тип (`embedded: true`).
- Квалификаторы отбрасываются: `account_use.InterestUse` хранится как
  `InterestUse` — резолвер сравнивает имена receiver'ов, а они без пакета.
- Не хранить типы полей-примитивов (`string`, `int*`, `bool`, `error`,
  `float*`, `byte`, `rune`): по ним всё равно нечего искать, а объём
  индекса режется заметно.
- **Не персистится.** Граф сохраняется через `to_json`/`from_json` уже
  с разрешёнными рёбрами, а индекс типов нужен только во время индексации.
  Это нужно написать в доке модуля, иначе первый же читатель решит, что
  забыли.
- Инвалидация в `remove_functions_for_file` — рядом с чисткой
  `name_index` и `file_path_lower_cache`.
- Тест: фикстура со структурой, интерфейсом, встроенным полем и алиасом;
  проверить, что квалификатор пакета отброшен, а примитивы не попали.
- Риск: память. Оценка — 4–6 тыс. типов на этом корпусе, единицы МБ.
  Замерить `memory_stats()` до/после.

## Э2. Объявленные возвращаемые типы (классы B, E и часть A)

- В `CallNode` добавить `#[serde(default)] pub result_type: Option<String>`
  — первый результат объявления. Для Go-кортежа `(T, error)` берётся первый
  не-`error` тип. Поле с `serde(default)`, персист совместим по построению
  (граф сериализуется целиком через serde).
- `expression_type_hint`: если инициализатор — вызов, разрешить его
  `resolve_scoped_callee` в текущем контексте и взять `result_type` узла;
  существующая эвристика по имени фабрики остаётся отступлением для
  вызовов, которых нет в графе.
- `chained_call_scope_hint`: там же и в том же порядке — сначала
  объявленный тип результата, потом имя фабрики. Это закрывает класс B:
  `accountRepo(ctx)` — обычная функция-хелпер, её имя ничего не говорит,
  а список результатов говорит всё.
- Многозначное присваивание (класс E): правая часть — один вызов, слева
  N имён; первое имя получает `result_type`, но только если остальные —
  `err`, `ok` или `_`. Иначе не угадываем.
- Резолюция помечается `Receiver`: тип прочитан из объявления, это факт,
  а не соглашение об именовании.
- Ожидание: −2500…3500 к `NameOnly`.

## Э3. Поля структур и цепочки через них (класс C и часть A)

- В `describe_callee`: если операнд — `selector_expression`, вычислить его
  тип: база (`self` → receiver текущего метода; идентификатор → таблица
  локальных) плюс поле → `TypeIndex`.
- Рекурсивно для `self.Depend.X.Y()`; ограничить глубину 4 звеньями, чтобы
  патологическая цепочка не съела проход.
- Отдельно проверить `self.Depend.<Поле>` — DI-контейнер этого проекта
  держит фабрики в полях, и часть класса A именно такая.
- Ожидание: −1500…2500.

## Э4. Встраивание структур (класс D)

- В `resolve_scoped_callee`, шаг 0: если по типу `T` одноимённого метода
  нет, обойти встроенные типы `T` в ширину (глубина ≤3) и искать там.
- Помечать `Receiver`: продвижение метода из встроенной структуры — правило
  языка, а не догадка.
- Осторожно с неоднозначностью: если метод нашёлся на двух встроенных
  типах одного уровня, Go считает это ошибкой компиляции — значит выбирать
  нельзя, возвращаемся к прежнему поведению.
- Ожидание: −1000…1300.

## Э5. Интерфейс → реализация

- Если выведенный тип — интерфейс (по `TypeIndex`) и узлов с таким
  receiver нет: сначала структура с тем же именем (конвенция этого
  проекта: `sfx.SfxOperationUse` ↔ `impl.SfxOperationUse`), затем
  единственный тип, чей набор методов покрывает методы интерфейса.
- Новая резолюция `InterfaceImpl`, `is_certain() == false`, caveat
  «single implementation of the interface». Несколько реализаций —
  оставляем прежнее поведение; веер рёбер по всем реализациям обсуждать
  отдельно, по умолчанию не расширять граф.
- На этом корпусе выигрыш небольшой (имена совпадают, работает уже
  сейчас), но на корпусе без такой конвенции это и есть разница между
  графом и его отсутствием.

## Э6. Наблюдаемость и защита от регресса

- Счётчики резолюций (`Unique`/`Receiver`/`Scope`/`FactoryReceiver`/
  `NameOnly`/`SameFile`/`Unresolved`) в `get_index_status` или
  `get_metrics`: сейчас деградация разрешения видна только тому, кто
  напишет измерительный тест руками.
- Бенчмарк `collect_calls` в `benches/`; бюджет — не более +50% ко
  времени сборки графа по сумме всех этапов. Текущая точка: 1,05 с на
  3232 файла.
- Тест-якорь: одна фикстура на ~10 файлов, покрывающая все шесть форм
  (self, локальная, фабрика, пакет, поле, встраивание), с проверкой
  именно `resolution`, а не только цели.

## Порядок и зависимости

```
Э1 (индекс типов)
 ├─ Э2 (возвращаемые типы) ──┬─ Э3 (поля, цепочки)
 ├─ Э4 (встраивание)         │
 └──────────────────────────-┴─ Э5 (интерфейс → реализация)
Э6 — параллельно, начиная со счётчиков перед Э2
```

Прогноз по сумме Э2–Э4: `NameOnly` 8449 → ориентировочно 2000–3500,
то есть догадок остаётся ~2% от рёбер против 6% сейчас и 11% до начала
работ.

## Что осталось после реализации

- Интерфейс с несколькими реализациями в индексе (граф не выбирает) или
  реализованный вне индекса.
- Значение из map, элемента срезa, канала, или из многозначного присваивания,
  где значимых имён больше одного.
- Переменная, переприсвоенная другим типом между объявлением и вызовом:
  чтение поверхностное, побеждает последнее объявление.
- Рефлексия, колбэки в переменных, вызовы платформой.
- Всё чтение объявлений — Go. Другие языки сохраняют разрешение по
  `self`/`this`, по имени фабрики и по файлу, но не получают шагов через
  поля, возвращаемые типы и интерфейсы.

## Границы

- Всё перечисленное — Go. Каркас (`TypeIndex`, возвращаемые типы) общий,
  но извлечение по-языковое: для Python поля класса живут в `__init__`,
  для TS — в объявлении класса и в интерфейсах, и это отдельная задача.
- Правило, которое нельзя нарушать ни на одном этапе: выведенный тип
  **предлагается** резолверу и отбрасывается, если на нём нет одноимённого
  метода. Иначе цена ошибки вывода — не «догадка вместо факта», а
  «уверенно неверная цель», что хуже прежнего поведения.
- Каждый этап проверяется на том же корпусе с выборочной ручной сверкой
  15–20 рёбер: цифры показывают сдвиг, но не показывают, куда именно
  уехали новые рёбра.
